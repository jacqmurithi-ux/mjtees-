# MJ Tees — schema, RPC and RLS review specification

**Status: review specification only. Not executable migration SQL.**  
Branch: `first-release-build` · Supabase project: `rbbluwsniiwzixlvdnwz`

This document translates the database design into a concrete first-release schema contract. It is for review before any migration is written or run. It does not authorize SQL execution, deployment, PR merge or live data entry.

## 1. First-release scope and explicit exclusions

Included: one business, one physical shop, owner account, public catalogue/enquiries, customers, quotations, order conversion, cash and manually entered M-Pesa, deposits/instalments, allocations, receipts, balances, inventory, purchasing/receiving, material costing, production tracking, quality checks, expenses, delivery/handover and audit trail. This is the complete owner-first operational release; staff-specific permissions can follow later.

**Tax is later.** No tax calculation, tax rate, tax line, tax registration setting or tax amount is included in the first-release quote/order/payment totals. The schema uses `subtotal_amount`, `discount_amount` and `total_amount` only. A future tax feature will be designed as a separately reviewed change; do not add a hidden default tax or silently change existing quote totals.

Deferred: automatic M-Pesa Daraja callbacks, SMS/WhatsApp and expanded staff access roles. Manual supplier purchasing, stock movements, production/QC, delivery and owner-only expenses are included in release one.

## 2. Common conventions

- UUID primary keys generated by the database.
- All business-owned records include `business_id NOT NULL`.
- Timestamps are `timestamptz NOT NULL DEFAULT now()`; display in Africa/Nairobi.
- Monetary amounts are integer KES (whole shillings) in release one. Never use float/double for money.
- Quantities are `numeric(12,3)` to support pieces, metres and square metres.
- Human-readable numbers are generated transactionally by a database sequence/counter scoped to the business and document type; never generated in React.
- Use `archived_at` for customer/catalogue archival. Do not hard-delete financial history.
- Foreign keys from a child to a business-owned parent use composite keys where practical: parent has `UNIQUE (business_id,id)`, child references `(business_id,parent_id)`.
- All status fields use explicit CHECK constraints or enums with documented transitions. Status changes are appended to event tables.
- Do not expose internal schema/functions through the public Data API by default. Put privileged helpers in a non-exposed schema.

## 3. Detailed first-release tables

### 3.1 Identity and business

**businesses**
- `id uuid PK`
- `name text NOT NULL`, `trading_name text`
- `currency_code char(3) NOT NULL DEFAULT 'KES' CHECK = 'KES'`
- `timezone text NOT NULL DEFAULT 'Africa/Nairobi'`
- `phone text`, `email text`, `address text`
- `is_active boolean NOT NULL DEFAULT true`
- `created_at timestamptz NOT NULL`, `updated_at timestamptz NOT NULL`
- `UNIQUE (id)`

**user_profiles**
- `user_id uuid PK REFERENCES auth.users(id) ON DELETE CASCADE`
- `display_name text`, `phone text`
- `created_at`, `updated_at`
- No role or business id is accepted from public user metadata.

**business_memberships**
- `id uuid PK`, `business_id uuid NOT NULL`, `user_id uuid NOT NULL REFERENCES auth.users(id)`
- `role text NOT NULL CHECK (role IN ('owner'))` for release one
- `status text NOT NULL CHECK (status IN ('active','suspended'))`
- `created_at`, `created_by uuid`
- `UNIQUE (business_id,user_id)`, `UNIQUE (business_id,id)`
- Owner membership created only by trusted bootstrap/admin process. No public self-assignment.

**audit_events**
- `id uuid PK`, `business_id uuid NOT NULL`, `actor_user_id uuid`
- `action text NOT NULL`, `entity_type text NOT NULL`, `entity_id uuid`
- `request_id uuid`, `occurred_at timestamptz NOT NULL DEFAULT now()`
- `metadata jsonb NOT NULL DEFAULT '{}'` with allowlisted keys; no secrets/payment credentials
- Insert only through trusted server/database operations; owner can read. Append-only.

**orders**
- `id uuid PK`, `business_id uuid NOT NULL`, `order_number text NOT NULL`

- `created_by uuid NOT NULL`, `created_at`, `updated_at`
- `UNIQUE (business_id,order_number)`, `UNIQUE (business_id,id)`
- Total is copied from accepted quote snapshot or owner-created direct order; amendment is evented and audited.

**order_items**
- `id uuid PK`, `business_id uuid NOT NULL`, `order_id uuid NOT NULL`
- `description text NOT NULL`, `quantity numeric(12,3) NOT NULL CHECK > 0`, `unit text NOT NULL`
- `unit_price bigint NOT NULL CHECK >= 0`, `line_discount bigint NOT NULL DEFAULT 0 CHECK >= 0`, `line_total bigint NOT NULL CHECK >= 0`
- `category_id uuid`, `customer_supplies_item boolean NOT NULL DEFAULT false`
- `sale_mode text NOT NULL CHECK IN ('blank','value_added')`, `production_method_id uuid`
- `production_specification jsonb`, `estimated_unit_cost bigint CHECK >= 0`, `actual_unit_cost bigint CHECK >= 0`
- `estimated_total_cost bigint CHECK >= 0`, `actual_total_cost bigint CHECK >= 0`
- `cost_breakdown_snapshot jsonb`, `cost_calculation_version text`, `created_at`
- Immutable accepted selling-price and cost-estimate snapshots; actual cost is finalized from job issues/cost entries. Amendments use separate events/records.

**order_events**
- `id uuid PK`, `business_id uuid NOT NULL`, `order_id uuid NOT NULL`
- `event_type text NOT NULL`, `from_status text`, `to_status text`
- `actor_user_id uuid`, `reason text`, `occurred_at timestamptz NOT NULL DEFAULT now()`
- Append-only. Handover/collection event only via guarded operation.

**payments**
- `id uuid PK`, `business_id uuid NOT NULL`, `payment_number text NOT NULL`
- `method text CHECK IN ('cash','mpesa_manual')`
- `status text CHECK IN ('pending_verification','posted','rejected','reversed')`
- `amount bigint NOT NULL CHECK > 0`, `currency_code char(3) NOT NULL DEFAULT 'KES'`
- `received_at timestamptz NOT NULL`, `payer_name text`, `payer_phone text`
- `mpesa_reference text`, `mpesa_reference_normalized text`, `intended_order_id uuid` (nullable only for non-order receipts; pending M-Pesa evidence retains its intended order here until verified)
- `idempotency_key uuid NOT NULL`, `received_by uuid NOT NULL`
- `verified_by uuid`, `verified_at timestamptz`, `notes text`, `created_at`
- `UNIQUE (business_id,payment_number)`, `UNIQUE (business_id,idempotency_key)`
- Unique partial index on `(business_id,mpesa_reference_normalized)` where method = mpesa_manual and reference is not null.
- Cash is posted at entry. M-Pesa is pending until owner verification. Rejected/reversed payments never count as paid.

**payment_allocations**
- `id uuid PK`, `business_id uuid NOT NULL`, `payment_id uuid NOT NULL`, `order_id uuid NOT NULL`
- `amount bigint NOT NULL CHECK > 0`, `created_by uuid NOT NULL`, `created_at`
- Unique/locking constraints enforced by transactional RPC; no direct client writes.

**allocation_reversals**
- `id uuid PK`, `business_id uuid NOT NULL`, `allocation_id uuid NOT NULL`
- `amount bigint NOT NULL CHECK > 0`, `reason text NOT NULL`, `reversed_by uuid NOT NULL`, `created_at`
- Total reversals cannot exceed original allocation. Append-only.

**payment_refunds**
- `id uuid PK`, `business_id uuid NOT NULL`, `payment_id uuid NOT NULL`, `order_id uuid`
- `amount bigint NOT NULL CHECK > 0`, `status text CHECK IN ('pending','posted','cancelled')`
- `reason text NOT NULL`, `refund_method text CHECK IN ('cash','mpesa')`
- `external_reference text`, `created_by uuid NOT NULL`, `posted_by uuid`, `posted_at timestamptz`, `created_at`
- Completed refunds cannot exceed posted unreversed payment value.

**payment_events**
- `id uuid PK`, `business_id uuid NOT NULL`, `payment_id uuid NOT NULL`
- `event_type text CHECK IN ('created','verified','rejected','reversed','refund_posted','allocation_reversed')`
- `actor_user_id uuid`, `reason text`, `metadata jsonb NOT NULL DEFAULT '{}'`, `occurred_at timestamptz NOT NULL DEFAULT now()`
- Append-only.

**receipts**
- `id uuid PK`, `business_id uuid NOT NULL`, `receipt_number text NOT NULL`
- `payment_id uuid NOT NULL`, `customer_name_snapshot text NOT NULL`, `amount bigint NOT NULL CHECK > 0`
- `currency_code char(3) NOT NULL DEFAULT 'KES'`, `issued_at timestamptz NOT NULL DEFAULT now()`, `issued_by uuid NOT NULL`
- `UNIQUE (business_id,receipt_number)`, `UNIQUE (business_id,payment_id)`
- Receipt issued only for posted funds; reprints reuse same receipt and are audited.

**order_balance** (read-only view in a non-public schema, or a tightly scoped security-invoker view)
- Per order: `order_id`, `order_total`, `net_paid`, `balance_due`.
- Net paid = sum of allocations for posted payments minus allocation reversals and posted refunds attributable to the order. A refund linked to a payment/order reduces the amount credited to that order; enforce aggregate refund and allocation-reversal limits under row locks so the same paid amount cannot be refunded and reversed twice. Pending M-Pesa and pending refunds are excluded.
- Balance is derived, not stored or browser-maintained.


### 3.5 Inventory, material costing and production (first release)

**Product and material model**

- An order line explicitly records sale_mode as blank or value_added. A catalogue item can be offered in either mode or both. Keep the sellable catalogue identity separate from the physical stock item/material used to make it.
- stock_items represents purchasable/consumable stock: blank garments, caps, mugs, hot-peel vinyl, sticker vinyl, sublimation paper/ink, screen-printing ink, emulsion, screens, transfer media, packaging and other supplies. Fields include business, SKU, name, stock type, base unit, purchase unit, conversion factor, default supplier, reorder point, active flag and timestamps.
- stock_variants supports size/colour/other variant attributes for blank products. Track each variant as its own stock-keeping unit; never combine different sizes/colours into one balance.
- inventory_locations are logical storage areas inside the one shop, not separate branches.
- stock_movements is append-only: purchase receipt, opening balance, issue to job, return, adjustment and transfer. Reservations are held in stock_reservations; waste is classified against issued material in production_waste. Each movement stores quantity, unit, unit cost snapshot, source reference, reason and actor. On-hand and available stock are derived from movements and reservations.
- Supplier purchases and goods receipts create stock only when goods are actually received. Use weighted-average cost for replenishable stock in release one and preserve receipt-time unit cost for audit and job-cost snapshots.

**Meter-based vinyl and sheet material costing**

For hot-peel vinyl, sticker vinyl and any material purchased in metres or rolls, store roll/material usable width in millimetres, purchase length in metres and purchase cost, usable width after edge/trim allowance, job cut width and height in millimetres, quantity and orientation/rotation permission, estimated layout/yield, actual linear metres consumed, offcuts returned to usable stock, and waste with a reason.

The estimator shows an efficient layout estimate and actual production consumption. Material cost = consumed linear metres × weighted-average cost per metre. For area-priced materials, derive consumed area from usable roll width × consumed length. Store layout inputs and outputs (usable width, cut dimensions, quantity, spacing/gap, rotation permission, estimated pieces per row, rows, linear metres and algorithm version) so the estimate is reproducible. Do not treat a simple rectangular yield estimate as guaranteed nesting; actual issued metres remain the cost basis. Material issued to a job is deducted once. Waste is a classification of that already-issued quantity, not a second stock deduction. Reusable offcuts returned to stock create a separate return movement and reduce net material cost charged to the job. Owner can override estimated consumption with actual issued quantity and a reason.

**Production and value-added costing**

- product_costing_profiles defines a recipe per catalogue item/category and sale mode (blank or value_added). A blank sale costs the blank item only. A value-added sale costs the blank item (unless customer-supplied), plus material and process components.
- costing_components supports blank_item, meter_material, area_material, consumable, machine_time, labour_time, outsourced_service, setup, packaging and other. Each component has a unit, a constrained driver type (per_piece, per_order, per_metre, per_square_metre, per_minute, per_hour, fixed_setup or manual), numeric factor, expected waste allowance and optional stock item. Do not store executable SQL/JavaScript formulas in the database; implement versioned calculation rules in application/backend code and snapshot their inputs and outputs.
- production_methods includes vinyl_cut, sticker_cut, sublimation, screen_printing, no_cut_printing, dtf_outsourced and configurable methods. Each process has its own setup, material, ink/consumable, machine-time and labour cost drivers.
- production_jobs links order line to method, quantity, planned/due/completed timestamps and status. production_material_issues snapshots actual stock quantity and unit cost. production_cost_entries captures labour, machine time, setup and outsourced work. production_waste records scrap, test prints, misprints, spoiled material and unusable offcuts.
- quality_checks record pass/fail, inspector, timestamp and notes. Prefer second-person inspection; allow self-inspection when one person is available and record it. Failed checks can create rework_events, whose additional materials/time are charged to the same order line/job.
- artwork_references stores Google Drive URL/file ID, filename, version, source and approval status only; artwork binaries remain in Drive.

**Actual cost and profit snapshots**

For every order line retain sale_mode (blank or value_added), selected production method, estimated_unit_cost, actual_unit_cost, estimated_total_cost, actual_total_cost, cost breakdown snapshot, selling price, discount and gross profit. The sale_mode must be fixed on the accepted order line; a blank sale cannot silently become value-added after acceptance without an order amendment.

Gross profit is net product-line revenue less direct actual cost (blank item/materials/consumables/labour/machine/setup/outsourcing/packaging attributable to the job). Net product-line revenue includes line discount and its allocated share of any order-level discount; delivery/carrier charges are excluded. The order discount allocation method must be deterministic (pro-rata by pre-discount line total, with any rounding remainder assigned to the final eligible line) and snapshotted at acceptance. Show estimated gross profit before production and variance after completion. Delivery/carrier charge is a separate customer-paid pass-through and is not production revenue or production cost. Customer-supplied garments have zero blank-stock cost but still incur decoration process costs. Later recipe changes never rewrite completed order costs.

**Expenses and delivery**

- expenses are owner-created in release one, with category, amount, date, payee, payment method, receipt reference, notes and audit. Shop overhead remains separate from direct job cost unless explicitly allocated to a job.
- deliveries stores collection/delivery method, carrier, tracking reference, customer-paid carrier charge, dispatch/handover timestamp and recipient. Carrier charges do not inflate product sales or production margin.


**Operational table contracts (all carry business_id, UUID identity, timestamps and business-scoped foreign keys unless noted)**

- **inventory_locations**: name, code, description, active flag. Logical storage areas only; not branches or separate businesses.
- **stock_items**: each independently counted SKU is a stock item, including every size/colour combination of a blank garment. Fields: SKU, name, optional parent_stock_item_id for grouping, variant_attributes jsonb (e.g. size and colour), stock_kind (blank_product/material/consumable/packaging), base_unit, purchase_unit, purchase_to_base_factor, costing_method (weighted_average), current_average_unit_cost, reorder_level, default_supplier_id, active/archived timestamps. Length materials store roll_width_mm and usable_width_mm. Enforce positive conversion factor and width for roll materials. Each variant SKU has its own movement balance; no separate stock_variants ledger is needed.
- **stock_movements**: stock_item_id, location_id, movement_type (opening, receipt, issue, return, adjustment, transfer_in, transfer_out), signed quantity in base unit, unit_cost_snapshot, source_type/source_id, reason, actor, occurred_at and request_id. Append-only; unique request_id per business. A transfer is paired movements in one transaction.
- **stock_reservations**: order_item_id, stock_item_id, location_id, reserved_quantity, released_quantity, status, created/released timestamps. Reservation does not create a stock movement or change physical on-hand; available = on-hand less active reservations.
- **suppliers**: display name, contact name, phone/email, notes, archived_at.
- **purchase_orders** and **purchase_order_items**: supplier, purchase number, status (draft/ordered/part_received/received/cancelled), ordered quantities, purchase unit, unit price, conversion snapshot and line total. Goods receipt, not purchase order creation, increases stock.
- **goods_receipts** and **goods_receipt_items**: purchase order reference, received_by, received_at, accepted quantity, rejected quantity, actual purchase unit cost, base-unit conversion and stock movement link. Partial deliveries supported.
- **production_methods**: stable code, name, active flag, setup-cost and process-driver configuration. Seed methods: vinyl_cut, sticker_cut, sublimation, screen_printing, no_cut_printing and dtf_outsourced. They are process templates, not hardcoded product categories.
- **product_costing_profiles**: optional catalogue item/category scope, sale_mode, production_method_id, version, effective dates, active flag. Exactly one applicable active profile chosen for a new estimate; existing order lines retain snapshots.
- **costing_components**: profile_id, component_type, optional stock_item_id, unit, driver_type, numeric factor, expected_waste_percent and fixed_cost. No executable formulas in data.
- **production_jobs**: order_item_id, production_method_id, status, planned_quantity, started_at, due_at, completed_at, estimate/actual cost totals, calculation version and notes.
- **production_material_issues**: job_id, stock_item_id, location_id, quantity issued in base unit, unit_cost_snapshot, extended_cost, stock_movement_id, issued_at, actor. This is the costed material issue ledger.
- **production_cost_entries**: job_id, cost_type (labour/machine/setup/outsourced/other), description, quantity, unit, unit_rate, amount, occurred_at and actor.
- **production_waste**: job_id, stock_item_id, quantity, waste_type, reason and related issue id. It classifies already-issued material; it is not a stock movement and must not create a second stock deduction.
- **production_offcut_returns**: job_id, stock_item_id, quantity, measured unit, destination location, stock_movement_id, condition and returned_at. Reusable offcuts are a stock return and credit to the job's net material cost.
- **quality_checks**: job_id, result (pass/fail), inspection_mode (second_person/self), inspector_user_id, checked_at and notes. Self inspection is permitted only as a recorded mode.
- **rework_events**: job_id, quality_check_id, reason, opened_at, closed_at, additional_cost snapshot and notes. Rework material/time is linked back to the originating order line.
- **artwork_references**: order_item_id, drive_url/file_id, filename, version_label, source, approval_status, approved_by and timestamps. No artwork file bytes stored in Supabase.
- **expenses** and **expense_categories**: owner-only category, payee, amount, date, payment method, receipt reference, optional notes and audit. Expenses are overhead unless explicitly linked to a job with a documented allocation.
- **deliveries**: order_id, method (collection/courier), carrier, tracking reference, customer_paid_charge, recipient, dispatched_at and handed_over_at. Carrier charge is a separate pass-through.

Stock movement and job cost rows are append-only. Corrections use compensating movements/cost entries with reason and actor, never silent edits or deletes. All quantity and cost snapshots are recorded in base units and integer KES respectively.

### 3.6 Numbering and concurrency

Use a `document_counters` table keyed by `(business_id, document_type)` for quote/order/payment/receipt sequences. Increment and return the next number inside the same transaction using row-level locking or atomic `UPDATE ... RETURNING`. Do not use `MAX(number)+1`, timestamps alone, or browser counters.

For quote conversion, lock the quotation row and verify it is accepted and not already converted before creating the order. For payment allocation, lock payment and order rows; re-check remaining unallocated payment and order balance inside the transaction. Idempotency key makes network retries safe.

## 4. RPC contracts (proposed exact public signatures)

All RPCs below are authenticated owner-only, except `submit_public_enquiry` and `accept_quote_by_token`. Functions validate `auth.uid()`, active membership, business scope and status transitions server-side. No function trusts client-supplied totals, role, receipt number, paid balance or verification status.

Use JSONB payloads for line arrays only where the function validates every key/type and rejects unknown fields. UUID request IDs are mandatory for retryable writes. Return a stable JSON object with identifiers and calculated totals. Exact SQL signatures will be frozen in migration after review.

### 4.1 Public enquiry

**`submit_public_enquiry(p_business_slug text, p_contact_name text, p_phone text, p_email text, p_requested_service text, p_description text, p_quantity numeric, p_desired_by date, p_customer_supplies_item boolean, p_artwork_drive_url text, p_request_id uuid) RETURNS jsonb`**

- Public: yes; no auth required. Strict rate limits/captcha or equivalent abuse controls at Edge Function boundary.
- Validates length limits, at least one contact channel, positive optional quantity, date not unreasonably old, URL allowlist and request id.
- Inserts enquiry only; never creates customer, quote or order.
- Returns `{ "ok": true, "public_reference": "...", "message": "Enquiry received" }`; no internal UUID or customer data.

### 4.2 Owner customer and quotation

**`owner_upsert_customer(p_business_id uuid, p_customer_id uuid, p_display_name text, p_business_name text, p_phone text, p_email text, p_notes text) RETURNS jsonb`**
- Owner only. Null customer_id creates; existing id updates. Cannot change business_id. Validates phone/email and length.
- Returns `{ "customer_id": uuid, "created": boolean }`.

**`owner_create_quote(p_business_id uuid, p_customer_id uuid, p_enquiry_id uuid, p_expires_at timestamptz, p_customer_notes text, p_internal_notes text, p_lines jsonb, p_request_id uuid) RETURNS jsonb`**
- Owner only. Each line allowed keys: catalogue_item_id, category_id, description, quantity, unit, unit_price, line_discount, customer_supplies_item, sale_mode, production_method_id, production_specification, pricing_rule_id. Validate sale_mode against the selected catalogue item; blank lines cannot silently include decoration costs, and value_added lines require a valid production method unless explicitly marked as a manual/non-production service. Server calculates and snapshots estimated unit/total cost and the versioned cost breakdown; client-supplied cost values are rejected.
- Server validates line values, category scope, quantity and discount; computes line totals, subtotal, discount and quote total. No tax.
- Returns `{ "quotation_id": uuid, "quote_number": text, "status": "draft", "subtotal_amount": bigint, "discount_amount": bigint, "total_amount": bigint }`.

**`owner_revise_quote(p_quotation_id uuid, p_expires_at timestamptz, p_customer_notes text, p_internal_notes text, p_lines jsonb, p_request_id uuid) RETURNS jsonb`**
- Owner only. Creates a new revision linked to prior quote; does not rewrite accepted/sent historical terms. Revision chain recorded.
- Returns new quotation id, quote number, revision reference and calculated totals.

**`owner_send_quote(p_quotation_id uuid, p_request_id uuid) RETURNS jsonb`**
- Owner only. Only draft quote can be sent; records sent event and creates single-use expiring acceptance token. Token is returned once for link delivery; only hash stored.
- Returns `{ "quotation_id": uuid, "status": "sent", "acceptance_url_token": "...", "expires_at": timestamptz }`. Token must not be logged.

**`accept_quote_by_token(p_token text, p_request_id uuid) RETURNS jsonb`**
- Public, narrowly scoped. Validates hash, expiry, unused token and sent quote; locks token/quote; atomically marks accepted and creates exactly one order plus order item snapshots. Repeated calls return existing conversion outcome without duplicate order.
- Returns `{ "accepted": true, "order_number": "...", "order_status": "confirmed" }`; no private notes or other customer records.

**`owner_accept_quote(p_quotation_id uuid, p_request_id uuid) RETURNS jsonb`**
- Owner-only alternative to public acceptance; same idempotent conversion and order creation rules.

### 4.3 Orders

**`owner_create_direct_order(p_business_id uuid, p_customer_id uuid, p_required_by date, p_promised_turnaround_hours integer, p_notes text, p_lines jsonb, p_request_id uuid) RETURNS jsonb`**
- Owner only. Each line accepts the same sale_mode, production_method_id, customer_supplies_item and specification fields as quote lines. Creates a direct order with server-side price and cost estimates; event reason/source records that it was owner-created, not quote-converted.
- Returns order id, order number, total and status.

**`owner_amend_order(p_order_id uuid, p_reason text, p_lines jsonb, p_request_id uuid) RETURNS jsonb`**
- Owner only. Requires reason; records before/after snapshots and order event. Never mutates the accepted original quotation. If payments already exist, recalculates balance atomically and rejects amendments that would create invalid allocations or requires explicit reallocation workflow.
- Returns order id, revised total and balance due.

### 4.4 Payments, receipts and balances

**`owner_record_payment(p_business_id uuid, p_order_id uuid, p_method text, p_amount bigint, p_received_at timestamptz, p_payer_name text, p_payer_phone text, p_mpesa_reference text, p_notes text, p_request_id uuid) RETURNS jsonb`**
- Owner only. Cash requires no M-Pesa reference and is posted immediately. M-Pesa requires a transaction reference and is created as pending_verification. Duplicate request id or normalized M-Pesa reference rejected/idempotently resolved.
- Cash: creates payment, allocation, receipt, payment event and audit event atomically.
- M-Pesa pending: creates payment evidence and event only; no allocation, receipt or paid-balance change.
- Returns `{ "payment_id": uuid, "payment_number": text, "status": "...", "allocated_amount": bigint, "receipt_number": text|null, "balance_due": bigint }`.

**`owner_verify_mpesa_payment(p_payment_id uuid, p_outcome text, p_reason text, p_request_id uuid) RETURNS jsonb`**
- Owner only. Outcome `verified` or `rejected`. Locks payment and order; can only verify pending M-Pesa. On verified, posts payment, allocates it to intended_order_id, creates receipt and audit/event records atomically. Reject if intended_order_id is missing or no longer has an allocatable balance; never let the verifier choose a different order at verification time. On rejected, marks rejected without affecting balance.
- Returns payment id, final status, optional receipt number and current balance due.

**`owner_reverse_payment_allocation(p_allocation_id uuid, p_amount bigint, p_reason text, p_request_id uuid) RETURNS jsonb`**
- Owner only. Positive amount, reason mandatory; cannot reverse more than remaining allocation. Adds immutable reversal; recomputes balance.
- Returns allocation id, reversed amount and current balance due.

**`owner_record_refund(p_payment_id uuid, p_order_id uuid, p_amount bigint, p_reason text, p_refund_method text, p_external_reference text, p_request_id uuid) RETURNS jsonb`**
- Owner only. Creates pending refund; posting is a separate operation to distinguish intent from money actually returned.
- Returns refund id and pending status.

**`owner_post_refund(p_refund_id uuid, p_request_id uuid) RETURNS jsonb`**
- Owner only. Verifies remaining refundable amount and posts refund; immutable event; balance due increases.
- Returns refund id, posted status and current balance due.

**`owner_get_order_balance(p_order_id uuid) RETURNS jsonb`**
- Owner only, scoped to caller's business.
- Returns `{ "order_id": uuid, "order_total": bigint, "net_paid": bigint, "balance_due": bigint, "currency_code": "KES" }`.

**`owner_get_payment_history(p_order_id uuid) RETURNS jsonb`**
- Owner only. Returns payment entries, status, allocations, receipt numbers, refunds/reversals and timestamps; never returns secret tokens.
- Supports pagination in implementation; stable ordering by occurred_at then id.

**`owner_reprint_receipt(p_receipt_id uuid, p_request_id uuid) RETURNS jsonb`**
- Owner only. Does not create a new receipt number; records reprint audit event and returns the existing receipt snapshot.

### 4.7 Purchase, production, costing and stock RPC contracts (fully scoped)

All are authenticated owner-only, derive actor from auth.uid(), validate business ownership, and accept p_request_id uuid for idempotency.

- **owner_receive_purchase(p_business_id uuid, p_supplier_id uuid, p_purchase_order_id uuid, p_received_at timestamptz, p_lines jsonb, p_request_id uuid) RETURNS jsonb** — line keys: purchase_order_item_id, stock_item_id, location_id, received_quantity, rejected_quantity, purchase_unit, unit_cost. Recompute conversion to base unit, reject negative quantities/costs, create goods receipt/items and receipt stock movements, update weighted average atomically. Only actually accepted goods increase on-hand.

- **owner_start_production_job(p_order_item_id uuid, p_method_code text, p_plan jsonb, p_request_id uuid) RETURNS jsonb** — one job per order item and production stage; validate method and specification, snapshot recipe version, estimate, vinyl layout inputs/outputs and algorithm version.

- **owner_record_job_waste(p_job_id uuid, p_stock_item_id uuid, p_quantity numeric, p_waste_type text, p_reason text, p_request_id uuid) RETURNS jsonb** — classify already-issued material only; reject waste quantity greater than remaining unclassified issue quantity; no second stock deduction.
- **owner_return_job_offcut(p_job_id uuid, p_stock_item_id uuid, p_location_id uuid, p_quantity numeric, p_condition text, p_request_id uuid) RETURNS jsonb** — return usable material as a compensating stock movement and credit its snapshot cost to the job; cannot return more than remaining unreturned issued material.

## 5. RLS and grants policy matrix

Enable RLS on every table in exposed schemas. The private schema containing helper functions/tokens/counters is not exposed through PostgREST. Policies use an indexed membership lookup based on `(select auth.uid())`; no authorization decision relies on `user_metadata`.

| Table/domain | anon | authenticated owner | Client writes |
|---|---|---|---|
| businesses | none | own business SELECT | none |
| user_profiles | none | own profile SELECT/UPDATE | own profile fields only |
| business_memberships | none | own membership SELECT | none |
| service_categories | published/active SELECT via public view only | own business SELECT | owner RPC only for mutations |
| catalogue_items | published/active SELECT via public view only | own business SELECT | owner RPC only for mutations |
| enquiries | submit via constrained function only; no SELECT | own business SELECT/UPDATE status | public function; owner RPC |
| customers, addresses | none | own business SELECT | owner RPC only |
| pricing_rules | none | own business SELECT | owner RPC only |
| quotations/items/events | acceptance token function only | own business SELECT | owner RPC only |
| orders/items/events | none | own business SELECT | owner RPC only |
| payments/allocations/events/refunds | none | own business SELECT | owner RPC only |
| receipts | none | own business SELECT | generated only by payment RPC |
| audit_events | none | own business SELECT | trusted operations only |
| stock items (including variant SKUs), locations, suppliers, purchase orders/items, goods receipts/items, movements, reservations | none | own business SELECT | owner RPC only |
| production methods/profiles/components, jobs, issues, waste, offcut returns, cost entries, QC, rework | none | own business SELECT | owner RPC only |
| expenses, expense categories, deliveries, artwork references | none | own business SELECT | owner RPC only |

### Policy predicates (normative, not migration SQL)

- Private row visibility: row's `business_id` belongs to an active `business_memberships` row for `auth.uid()`. For release one, require `role = 'owner'` and `status = 'active'`.
- Profile visibility/update: `user_id = (select auth.uid())`; column grants prevent user from editing identity/role fields.
- No direct INSERT/UPDATE/DELETE grants to authenticated on financial tables, quotations, orders, enquiry rows or event ledgers. RLS policies alone are insufficient if table grants remain broad.
- Public catalogue uses a security-invoker view or narrow read function exposing only published fields; do not expose base table rows with hidden/internal columns.
- Public enquiry submission is an RPC/Edge Function only. Revoke direct table INSERT/SELECT for anon.
- Token table, counters, audit helper and private functions live in a non-exposed schema; revoke schema usage from anon/authenticated unless a specific function is deliberately granted.
- Owner RPC execute privileges are granted only to authenticated; each function checks active owner membership itself. Public functions are the only exceptions and expose constrained operations.

### Required RLS policy shapes (illustrative SQL predicates)

```sql
-- The following are policy predicate shapes for review, not a complete migration.
-- A helper such as private.is_active_owner(business_id) must itself be safe,
-- non-recursive, indexed, and inaccessible as a general-purpose data oracle.

USING (
  exists (
    select 1
    from public.business_memberships m
    where m.business_id = <table>.business_id
      and m.user_id = (select auth.uid())
      and m.role = 'owner'
      and m.status = 'active'
  )
)
```

For user profile:
```sql
USING (user_id = (select auth.uid()))
WITH CHECK (user_id = (select auth.uid()))
```

No anonymous policy is created on private business tables. Public catalogue access is through a restricted projection. Public enquiry write is through the function only, not a table policy.

## 5. Function security and implementation rules

- Prefer `SECURITY INVOKER`. If a function must be `SECURITY DEFINER`, place it in a non-exposed schema, pin `search_path` to trusted schemas, schema-qualify objects, explicitly validate `auth.uid()` and active owner membership, revoke EXECUTE from PUBLIC/anon, and grant only to the intended role.
- Every owner function derives actor from `auth.uid()`; never accept actor/role from the client.
- Use transaction boundaries inside each RPC; exceptions roll back payment, allocation, receipt and audit writes together.
- For idempotent operations, persist `request_id` and the result reference under a unique constraint. Repeated requests return the original outcome, not a second payment/order.
- Do not return acceptance tokens from logs or audit metadata. Hash at rest and single-use.
- Never expose Supabase service-role/secret keys to GitHub Pages. Browser has only publishable key and user session.
- Use explicit column grants for profile updates; user must not edit membership, payment status, totals, audit or verification fields.

## 7. Mandatory test cases before approval

1. Anonymous user cannot select customers, enquiries, quotes, orders, payments or receipts.
2. Anonymous user can submit a valid enquiry but cannot read it back or create a customer/order.
3. Authenticated non-member cannot read any business row or call owner RPCs successfully.
4. Owner can create/update a customer and see only own business data.
5. Client-supplied quote totals are ignored; database recomputes all line and quote totals.
6. Quote acceptance token expires, is single-use and cannot create two orders under concurrent requests.
7. Accepted quote terms remain unchanged after later pricing rule changes.
8. Cash payment posts once, allocates once, creates one receipt and reduces balance correctly.
9. M-Pesa pending entry does not allocate, create receipt or reduce balance.
10. Verified M-Pesa posts, allocates and issues exactly one receipt; rejected M-Pesa has no balance effect.
11. Duplicate idempotency key cannot create a second payment or receipt.
12. Duplicate normalized M-Pesa reference is rejected across retries.
13. Allocation cannot exceed posted payment remainder or order balance, including concurrent attempts.
14. Reversal/refund cannot exceed the original posted amounts and never deletes source rows.
15. Receipt reprint preserves the receipt number and records an audit event.
16. Owner membership cannot be self-created from signup metadata.
17. A caller cannot pass another business_id to access or mutate that business.
18. No tax is applied in any quote/order/payment calculation in release one.
19. Pending M-Pesa evidence retains its intended order and cannot be allocated to a different order during verification.
20. A stock reservation reduces available quantity but not physical on-hand; releasing it restores availability without a movement.
21. Waste classification never deducts stock a second time; reusable offcut return creates one compensating stock movement and credits job cost once.
22. Two concurrent issues cannot consume the same available stock; the second request fails safely or returns its idempotent result.
23. Every blank garment size/colour SKU has an independent stock balance and average cost.
24. Quote acceptance copies sale mode, production method, customer-supplied flag and cost-estimate snapshot to immutable order lines.
25. Order-level discount is allocated deterministically to lines before gross-profit reporting; rounding remainder is reproducible.

## 9. Costing acceptance tests (additional mandatory cases)

1. A blank T-shirt sale consumes the correct size/colour variant and has no decoration costs.
2. A value-added T-shirt sale includes the blank garment plus the selected decoration process.
3. Customer-supplied apparel does not consume or cost a blank garment, but decoration materials and production costs are captured.
4. Vinyl estimator calculates expected linear metres from roll width, cut dimensions, quantity, orientation and usable width; actual issue can override estimate with a reason.
5. Sticker and hot-peel vinyl waste is charged to the job; reusable offcuts returned to stock are credited and not double-charged.
6. Sublimation cost includes blank substrate (unless customer-supplied), paper, ink/consumables, setup, machine/labour time and recorded spoilage.
7. Screen-printing cost supports setup/screen preparation, emulsion, ink, screens/consumables, print run and spoilage; per-unit cost changes with run quantity.
8. No-cut printing cost uses its own process profile and material/ink/outsourcing drivers, not the vinyl-cut workflow.
9. Production rework adds actual material/time cost to the original job and reduces gross profit.
10. Recipe or supplier-cost changes do not rewrite completed order cost snapshots.
11. Stock reservations do not reduce physical on-hand; issues do. Returns, waste and adjustments reconcile correctly.
12. Weighted-average material cost updates on receipts and is applied consistently to issues.
13. Direct job costs are distinct from overhead expenses; carrier delivery charge is separate from sales and production margin.
14. Reports show estimated vs actual cost and gross profit by order line, order, category, sale mode and production method.
